# Report Management Specification

> This document defines the complete lifecycle of citizen reports in CivicConnect.
>
> It is the authoritative specification for report submission, processing, tracking, AI analysis, and resolution.

---

# Overview

A report represents a civic issue submitted by a citizen.

Examples include

- Potholes
- Garbage collection
- Water leakage
- Drainage blockage
- Broken streetlights
- Illegal dumping
- Road damage
- Public sanitation
- Tree hazards
- Traffic signal failures

Each report progresses through a controlled lifecycle from submission to resolution.

---

# Objectives

The reporting system must provide

- Easy issue reporting
- Accurate location capture
- AI-assisted validation
- Department routing
- Transparent status tracking
- Complete audit history

---

```
↓

```

```
Rejected

Duplicate

```

## Issue Details

- Title

- Language

- Urgency

---

## Location

- Latitude
- Longitude
- Address
- Ward
- Zone

---

## Images

---

## AI Metadata

- Summary

- Moderation result
- Forensic result

# Report Submission Workflow

```
Citizen Creates Report

↓

Validate Request

↓

Store Report

↓

Upload Images

↓

Queue Background Processing

↓

Return Tracking ID

↓

AI Processing Begins
```

Report submission should return immediately.

Long-running AI tasks execute asynchronously.

---

# Validation Rules

A valid report requires

- Authenticated citizen
- Valid issue category
- Description
- Valid location
- At least one image (configurable)

The backend performs validation before storing the report.

---

# Image Upload

Supported formats

- JPEG
- PNG
- WEBP

Maximum image count

Configurable.

Maximum file size

Configurable.

Images are stored using the media service.

---

# AI Processing Pipeline

After submission

```
Validation

↓

Forensics

↓

Classification

↓

Geo Validation

↓

Moderation

↓

Enhancement

↓

Department Routing

↓

```

The AI pipeline operates asynchronously.

---

# Duplicate Detection

The system may detect duplicate reports using

- Location proximity
- Similar description
- Similar images
- Existing unresolved reports

Duplicate reports are flagged for review.

The original report remains unchanged.

---

# Department Assignment

Each verified report is assigned to the appropriate department.

Assignment considers

- Issue category
- Geographic boundary
- Ward
- Urgency
- Routing rules

Assignment history is retained.

---

# Status Updates

Citizens receive updates when

- Report submitted
- Report verified
- Department assigned
- Work started
- Issue resolved
- Report rejected

Notifications are delivered asynchronously.

---

# Resolution

A report may be marked resolved when

- Department confirms completion
- Required evidence is available
- Resolution satisfies business rules

Resolved reports remain visible in history.

---

# Citizen Actions

Citizens can

- Submit reports
- View reports
- Track status
- Upload additional images (if permitted)
- View resolution details
- Cancel eligible reports

Citizens cannot modify verified reports.

---

# Department Actions

Authorized staff may

- Accept assignments
- Update status
- Add resolution notes
- Upload completion images
- Escalate reports
- Reassign reports (if permitted)

Every action is audited.

---

# AI Generated Fields

The system generates

- English translation
- Report summary
- Issue classification
- Confidence score
- Department recommendation
- Moderation result
- Image forensic result

Original citizen content is never overwritten.

---

# Geolocation

Every report stores

- Latitude
- Longitude

The backend derives

- Ward
- Zone
- Administrative boundary

Spatial calculations use PostGIS.

---

# Search

Reports should support filtering by

- Status
- Category
- Ward
- Date range
- Citizen
- Department
- Priority

Sorting options

- Newest
- Oldest
- Priority
- Status

Pagination is required.

---

# Rewards Integration

Eligible reports may earn reward points.

Rewards depend on

- Valid submission
- Unique issue
- Successful verification

Reward rules are defined separately.

---

# Notifications

Events generating notifications

- Submission
- Assignment
- Status update
- Resolution
- Rejection

Notification delivery failures must not affect report processing.

---

# Audit Requirements

Every report event is recorded.

Examples

- Submission
- Status changes
- Assignment
- AI decisions
- Resolution
- Cancellation

Audit records are immutable.

---

# Error Handling

Examples

- Invalid category
- Invalid location
- Upload failure
- AI processing failure
- Department unavailable

Errors must return standardized responses.
